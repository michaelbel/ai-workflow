description: >-
  Тонкий CoroutineWorker вызывающий бизнес-UseCase через getOrThrow, планирование и отмена в
  отдельных UseCase, constraints, unique work и retry policy
paths:
  - "**/*.kt"
---

- Реализуй фоновую задачу как тонкий `CoroutineWorker`: worker читает и проверяет входные данные,
  вызывает существующий бизнес-`UseCase` через `.getOrThrow()` и преобразует итог в
  `Result.success()`, `Result.retry()` или `Result.failure()`. Для чисто Android-системной операции,
  например показа локального уведомления, worker может вызвать системный API напрямую, но не должен
  содержать бизнес-решения фичи.
- Планирование и отмену работы размещай в отдельных `UseCase` в `shared/domain/usecase`; не
  запускай новую работу из `companion object` worker и не передавай `WorkManager` во ViewModel.
- Для внедрения зависимостей следуй существующей Hilt-конвенции проекта: используй `@HiltWorker` и
  `@AssistedInject`, когда настроен `HiltWorkerFactory`, либо существующий Hilt `EntryPoint`, когда
  проект получает зависимости worker таким способом. Не создавай параллельную фабрику.
- Выбирай `enqueueUniqueWork` / `enqueueUniquePeriodicWork`, только если задача имеет естественный
  стабильный identity. Имя unique work и теги должны быть стабильными; выбирай
  `ExistingWorkPolicy` или `ExistingPeriodicWorkPolicy` по продуктовой семантике сохранения, замены
  или продолжения существующей работы, а не по удобству реализации.
- Передавай через `Data` только небольшой набор примитивов и строк. Храни крупный payload и
  состояние повторяемой операции в Room, а в worker передавай стабильный идентификатор записи.
- Объявляй только необходимые `Constraints`. Не требуй сеть для локальной работы и не добавляй
  initial delay, backoff или periodic execution без требования сценария.
- Настраивай backoff для действительно повторяемых ошибок. Ограничивай собственные retry по
  `runAttemptCount`, если бесконечные повторы не являются явной частью продукта.
- Возвращай `success` после завершённой или идемпотентно уже выполненной операции, `retry` только для
  временной ошибки, а `failure` — для некорректного input и постоянной ошибки. Не превращай любую
  ошибку в `retry`.
- Никогда не поглощай `CancellationException` и не преобразуй отмену worker в `retry` или
  `failure`; освобождай ресурсы и пробрасывай отмену дальше.
- Делай повторяемую операцию идемпотентной или защищай её серверным/локальным operation id, потому
  что WorkManager гарантирует выполнение, но не exactly-once семантику бизнес-операции.
- Для отмены используй тот же unique work name или стабильный tag/id, который задаёт scheduling
  use case. Не дублируй строковые ключи между worker и use case: держи относящиеся к задаче
  константы рядом с владельцем scheduling-контракта.
- Для account/session-scoped работы включай identity владельца или generation сессии в unique work
  и input. Отмена при logout является best effort: worker обязан повторно проверить актуальную
  сессию перед сетевым вызовом и перед записью результата в Room, чтобы старая работа не записала
  данные после logout или смены пользователя.
