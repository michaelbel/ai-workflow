# Notion Guide Rules

## Место публикации

Сначала ищи существующую страницу по точному или близкому названию. Если она найдена, обновляй только её: не создавай дубликат и не переноси страницу между базами.

Если страницы ещё нет, по умолчанию создавай её в data source с точным именем `POSTS`, если пользователь явно не указал другое место. Разрешай страницу и data source через Notion API по имени или предоставленному пользователем URL. Не сохраняй внутренний Notion ID в публичном репозитории.

## Язык и заголовок

Страница пишется на русском.

Шаблон названия:

```text
Гайд по <Topic>. <Практический результат>
```

Примеры:

- `Гайд по Insets. Как обрабатывать отступы и вырезы`;
- `Гайд по ListItem. Как проектировать экспрессивные списки`;
- `Гайд по EyeDropper. Как использовать системную пипетку в Android 17`.

Не повторяй title первым заголовком в content: Notion показывает свойство title автоматически.

Если широкая тема поддерживает несколько API или способов представления, а проект разбирает только один из них, укажи выбранный API в title. Не создавай впечатление, что гайд покрывает всю тему.

## Вступление

До первого `##` напиши один-два плотных абзаца:

- что это за API;
- какую проблему он решает;
- когда разработчик сталкивается с этой проблемой;
- главное ограничение или условие, если оно критично.

В первом абзаце повторно зафиксируй точный объем гайда. Разделяй системную capability или treatment и конкретный presentation API: не называй их одним механизмом и не подменяй одно другим.

При первом употреблении специального термина объясни его простыми словами через наблюдаемое поведение. Не заменяй объяснение другим абстрактным термином: вместо общих формулировок вроде `заметные поверхности` перечисли конкретные места интерфейса, если их немного.

Не перечисляй варианты API, которые не рассматриваются в гайде, только ради полноты. Упоминай их лишь тогда, когда без этого нельзя корректно объяснить границы или поведение выбранного API.

Не начинай с истории библиотеки, общих слов или определения Android.

## Структура

Не используй один жесткий набор разделов для всех тем. Строй страницу вокруг ментальной модели и публичного API.

Рекомендуемый порядок:

1. главная идея;
2. настройка manifest, если API требует permissions, services, activities или providers;
3. основные компоненты и методы API;
4. параметры, состояния и варианты с кодом из проекта;
5. документация.

Не добавляй отдельные служебные разделы `Требования и версии проекта`, `Сценарии проекта` и `Состояние, жизненный цикл и завершение`. Не добавляй таблицу версий проекта. Упоминай минимальную версию Android, статус API или версию тематической библиотеки рядом с тем API, для которого эта информация необходима.

Если нужны разрешения, выноси их в отдельный раздел `Настройка манифеста` с фрагментом manifest и объяснением каждого permission.

Основные секции API оставляй открытыми. Не превращай описания компонентов и методов в toggle. Toggle допустим только для длинной повторяющейся справочной информации, которая не является основным содержанием гайда.

Самостоятельную пользовательскую операцию, например открытие системных настроек, выноси в отдельный H2, если для нее нужны отдельная настройка manifest и код вызова. Сначала показывай требуемый фрагмент manifest, затем код операции и объяснение проверки доступности.

## Описание компонента

Для каждого важного компонента ответь:

- что делает;
- где находится в общем потоке;
- какие параметры важны;
- какой минимальный пример это показывает;
- какие есть состояния, ограничения и ошибки.

Не пересказывай сигнатуру параметр за параметром, если параметр очевиден.

Если H2 уже содержит имя метода, класса или типа, не начинай первый абзац с повторения того же имени. Сразу объясняй назначение, поведение или результат.

Если API предоставляет набор semantic styles, режимов или констант, описывай каждое значение отдельным пунктом маркированного списка.

## Стиль

- Пиши коротко и конкретно.
- Обращайся к читателю на «ты».
- Не используй букву `ё` или `Ё`. Всегда пиши `е` или `Е`.
- Выделяй имена API, параметры, значения и другие технические термины оранжевым: `<span color="orange">` в Notion Markdown.
- Каждый технический термин в inline code оформляй как `<span color="orange">` + inline code. Не оставляй технические термины в обычном inline code, который Notion показывает красным.
- Не используй красный цвет для терминов. Все цветные выделения API, параметров и значений делай оранжевыми.
- Не выделяй оранжевым целые предложения.
- Используй inline code для классов, функций, параметров и значений.
- Код — в блоках `kotlin`, `xml`, `toml` или `shell`.
- Не используй длинное тире `—`. Используй среднее тире `–`.
- Не используй выражение `строка состояния` и его падежные формы. Используй `статус бар`.
- Перед каждым заголовком H2 добавляй отдельный пустой Notion-блок `<empty-block/>`.
- Не добавляй буквальный текст `#<empty-block/>`, `#\<empty-block/\>` или другие экранированные варианты. `<empty-block/>` должен быть отдельным блоком и визуально отображаться как пустая строка.
- Не добавляй callout-блоки без явного запроса пользователя. Важные условия и предупреждения пиши обычными абзацами рядом с соответствующим API.
- Каждый пункт маркированного и нумерованного списка начинай с заглавной буквы.
- Не создавай отдельный раздел `Ограничения demo-проекта`. Существенные ограничения API размещай в разделах соответствующих компонентов или сценариев.
- Скриншоты и GIF добавляй только там, где поведение важно увидеть.
- Не добавляй раздел «Итоги» ради формальности.

## Код и ссылки

- Пиши страницу после реализации проекта.
- Большой фрагмент кода должен существовать в репозитории.
- Если пример использует `resolveActivity()` или другой запрос к `PackageManager`, проверь требования package visibility. Когда нужен `<queries>`, покажи его рядом с кодом `Intent` и используй ту же action, что реализована в проекте.
- Не упоминай в тексте названия, номера и файлы samples, например `Sample07` или `Sample07App.kt`.
- Не добавляй ссылки на отдельные sample-файлы. Встраивай кодовые примеры в описание соответствующего API, а в разделе `Документация` оставляй ссылку на репозиторий.
- Не превращай упоминания файлов в GitHub-ссылки внутри основного текста. Имена файлов пиши обычным текстом, если пользователь явно не попросил точную ссылку.
- Версия зависимости должна совпадать с `libs.versions.toml`.
- Не используй ссылки на временные ветки.
- В конце добавляй H2 `Документация`.
- Перед `## Документация`, как и перед любым H2, добавляй отдельный `<empty-block/>`.
- Ссылки на `developer.android.com` размещай отдельными строками без списка в формате Notion link mention: `[Заголовок страницы | Android Developers](<url>)`.
- После ссылок на документацию добавляй отдельную строку `Репозиторий – [<repository-url>](<repository-url>)`.
- Не добавляй в конец страницы служебный отчёт о commit SHA, Gradle, lint, GuideKit validator или статусе публикации. Эти данные хранятся в `.guidekit/validation-report.md` и финальном ответе агента.

## Разделение ответственности

README кратко показывает проект и список samples. Notion подробно объясняет API без упоминания названий, номеров и файлов samples. Не копируй целые разделы между ними.
